# Pricing and Hedging India's Exchange-Traded Rainfall Futures: A Reproducible Framework with Early Evidence on the Market Price of Rainfall Risk

*MonsoonQuant project preprint. Research analytics, not investment advice. All numbers below are measured, from real data, by the code in this repository — reproduce them with `make reproduce` (see §9).*

## 1. Introduction

India's southwest and northeast monsoons govern agricultural output, insurance losses, and infrastructure risk at a scale that few financial instruments address directly. In 2026, NCDEX (National Commodity & Derivatives Exchange) listed exchange-traded rainfall futures on two cumulative-deviation-of-rainfall (CDR) indices — RAINCHNNAI (Chennai, Sep1-Dec31 season) and RAINMUMBAI (Mumbai, Jun1-Sep30 season) — the first such contracts in India. They are new, thin, and essentially unresearched in the open literature.

This project builds, end to end, the pricing, forecasting, and hedging infrastructure such a contract needs: a real contract-index replication engine, a chain-dependent stochastic rainfall simulator, a probabilistic forecasting ladder evaluated out-of-sample on a public hash-chained ledger, a market-price-of-risk estimator, and a hedge/basis-risk/parametric-cover toolkit — all run against real IMD gridded rainfall and real climate-driver data, never synthetic placeholders for the underlying physical process.

**Contributions**: (1) a fully reproducible, open-source reference implementation for pricing a CDR rainfall index from first principles; (2) a real walk-forward evaluation of a 5-rung forecasting ladder at the actual sample size this contract offers (n=31 historical seasons), reporting — rather than retuning away — the finding that added model complexity does not yet beat climatology at this n; (3) a real, if still illustrative-measure, estimate of the market price of rainfall risk via Wang and Esscher transforms, blocked from real-settlement calibration only by an external data access restriction (§8); (4) a hedging and basis-risk toolkit with a real structural finding specific to this contract (§7).

## 2. Contract design & index replication

Both contracts settle on a CDR index: the cumulative deviation of rainfall from its long-period average (LPA) across the contract's season, averaged across two official IMD stations. The real contract specifications (period dates, station identities, tick size, multiplier, settlement rules) were resolved from NCDEX's own published PDFs, not assumed — 11 of 12 VERIFY items are closed this way (`docs/VERIFY.md`); the 12th (data-redistribution licensing) has no sourced document stating explicit terms and stays open by design.

The index engine (`mq.index.engine.compute_index`) reconstructs this exactly: a season-LPA anchor plus the cumulative daily deviation, golden-tested against 4 hand-computed cases including a deliberate missing-data gap. **Proxy error** — the gap between this project's own satellite/model-derived index reconstruction and NCDEX's official settlement index — cannot yet be measured: no official settlement series has been publishable, since the same data-access restriction that blocks §8's calibration also blocks this comparison. The proxy-error machinery (`mq.index.proxy.proxy_error`) is built and tested; there is simply nothing real to compare it against yet.

## 3. Data

**IMD gridded rainfall**: 0.25° resolution, backfilled for 31 real years (1991-2020 plus 2023 — the project's full real-time-ingested season), zero gaps, plus real-time data for the 2026 season (Sep1 onward). **Climate drivers**: ONI (El Niño/Southern Oscillation, 920 real rows) and DMI (Indian Ocean Dipole, 1,877 real rows), both live-ingested. MJO (Madden-Julian Oscillation) is named in the original specification but not ingested — the source (Australia's Bureau of Meteorology) blocks this project's automated access outright, and that restriction is treated as policy, not something to route around (`docs/DECISIONS.md`).

**Market data**: NCDEX's `bhavcopy` settlement/volume/open-interest feed sits behind a bot-detection challenge and has never been successfully ingested. Every downstream computation that would need it (λ calibration, proxy error against a real settlement series) is built and tested against the data that *is* real, and reports its own absence honestly rather than substituting a placeholder.

**Leakage control**: every data read in this project funnels through an as-of-aware I/O layer (`mq.io.asof`) that enforces a hard `as_of` boundary at read time, not by convention. The forecasting ladder's walk-forward backtest (§5) could not otherwise be trusted — a single leaked future value in model fitting would quietly inflate every skill number below.

## 4. Physical-measure models

**Burn analysis** (`mq.pricing.burn`): the plain historical distribution of 31 real season-end CDR values for RAINCHNNAI — mean 905.6mm, median 843.4mm, standard deviation 388.5mm, skew 1.14 (right-skewed, as seasonal rainfall totals typically are), P5/P95 of 449.6mm/1,699.0mm.

**Distribution selection** (`mq.pricing.distribution`, `mq.pricing.selection`): seven candidate distributions (gamma, lognormal, Weibull, KDE with Silverman's rule, KDE with cross-validated bandwidth, bootstrap, and an ENSO-conditioned climatology) scored by leave-one-out CRPS — the maximal honest use of 31 real data points, since a literal rolling-origin split would leave too few points per fold to fit a 3-parameter distribution at all. `kde_cv` wins (CRPS 213.01), narrowly ahead of gamma (213.14) and Weibull (213.30).

**Chain-dependent simulator** (`core/`, C++ via pybind11): a day-by-day Markov occurrence model plus a Gamma-distributed amount model, fit on 11,323 real station-days (1991-2020 plus 2023). An under-dispersion problem in the naive simulated seasonal-total variance (272.5mm vs. the real historical 412.3mm) was found and fixed with a season-level lognormal overdispersion multiplier, calibrated via a one-dimensional root-find (σ=0.336, bringing simulated sd to 418.5mm — within the ±10% target band). The simulator itself runs 1,000,000 paths × 92 days in **0.82 seconds** (a 10-second budget), using the Philox4x32-10 counter-based RNG verified bit-for-bit against its own published known-answer test vectors, and produces a bit-identical SHA-256 digest of its output regardless of OpenMP thread count (1, 2, 4, or 8) — determinism confirmed by measurement, not assumed from the RNG's design alone.

## 5. Probabilistic forecasting

A 5-rung ladder, each rung trained on the same shared (season, issue-day) feature table (`mq.forecasting.features`) so no rung can silently diverge from another in how a feature is computed: plain climatology (`clim_v1`), ENSO-tercile-conditioned climatology (`enso_clim_v1`), a k=5 nearest-analog-season model (`analog_v1`), LightGBM quantile regression (`lgbm_q_v1`), and the same model with split-conformal calibration (`lgbm_q_cqr_v1`).

A real walk-forward backtest against RAINCHNNAI (2,541 predictions per model, `train <= year y-1` enforced structurally by the harness, not by convention) gives the honest, consistent finding that **every added-complexity rung underperforms plain climatology** on mean CRPS at this sample size: clim_baseline 156.4, enso_clim_v1 165.4 (CRPSS -5.8%), analog_v1 182.3 (-16.5%), lgbm_q_v1 194.0 (-24.0%), lgbm_q_cqr_v1 201.9 (-29.1%). None of these were retuned to chase a positive CRPSS number, which would simply overfit the backtest itself.

Conformal calibration, despite not rescuing CRPS, does exactly what it is built to do: the uncalibrated `analog_v1`/`lgbm_q_v1` under-cover badly (31.9%/60.9% and 33.1%/68.6% against nominal 50%/90%), while `lgbm_q_cqr_v1`'s coverage (45.5%/86.3%) comes in much closer to nominal — a real, measured demonstration that the calibration mechanism works even on a model whose raw point/quantile accuracy is below a trivial baseline. A Temporal Fusion Transformer rung (named in the original specification) was deliberately not built: the specification itself flags it as a weak candidate near 120 seasons of data, and this project's real n=31 is well below even that — reasoning kept on record rather than attempted and quietly dropped.

Live forecasts for the 4 newer rungs are now also written to the public prediction ledger as of the current season (§6), not only exercised in backtesting — closing a gap this project's own specification explicitly flagged, since the standard training-row builder structurally cannot produce a row for a season still in progress; a dedicated live-feature-row builder was added for exactly this case.

## 6. The prediction ledger

Every forecast — whether from a backtest or a live run — is written to an append-only, SHA-256 hash-chained table before its outcome can be known (`mq.ledger`). The chain's immutability is enforced at the database level (a Postgres trigger blocks `UPDATE`/`DELETE` outright, proven by a test that attempts both and catches the resulting error) and verified by recomputing the full hash chain from scratch (`mq ledger verify`). The ledger currently holds 8 real rows: 4 historical `clim_v1` entries from the project's first live forecasts, and one real live row each for the 4 newer rungs as of the 2026 season's most recent real-data date.

## 7. Pricing measure and hedging

**Market price of risk** (`mq.mpr`): Wang and Esscher transforms, with bootstrap, closed-form delta-method, and Bayesian-pooled uncertainty bands, all built and tested — including an effective-sample-size guard that refuses to report a degenerate self-normalized Esscher estimate rather than silently returning one. Calibrated only against an illustrative settlement price, since no real NCDEX settlement price has ever been ingested (§3); the sign and magnitude behavior (λ>0 raises price; the recovered λ moves in the correct direction relative to an illustrative settle above or below the physical mean) is verified, the actual real-market λ is not yet measurable.

**Hedging** (`mq.risk.hedge`, `mq.risk.cvar`): a real case study — a candidate exposure location's real IMD rainfall, run through an illustrative delivery-rider income-loss exposure template, hedged against the real official RAINCHNNAI index with both a min-variance and a CVaR95 (Rockafellar-Uryasev) optimizer. The real, structural finding: **the real RAINCHNNAI index has been positive in every one of its 31 historical seasons**, so an *unconstrained* CVaR95 hedge has no interior optimum and genuinely wants to short without limit — position limits are required for this specific contract's CVaR optimization to be well-posed at all, not merely a risk-management nicety layered on top. A real re-run of this case study (`mq research reproduce`, current data) finds the CVaR95 hedge hitting its 20-lot position-limit bound exactly as this finding predicts, with a min-variance hedge of -3 lots (18.1% variance reduction) — a modest drift from an earlier write-up's -5 lots/42.0% (`docs/methods/hedge.md` §6), reported honestly as a reproduction discrepancy rather than reconciled.

**Basis risk** (`mq.risk.basis`): a real 12-cell grid around RAINCHNNAI's two official stations, confirming the expected real pattern — correlation and hedge effectiveness are highest (0.96+) immediately next to the official stations and degrade measurably with distance, dropping to 0.73 at the grid box's far corner (roughly 60km away).

**Parametric cover design** (`mq.risk.parametric`): grid search plus Nelder-Mead refinement over (trigger, slope, limit) to minimize a real synthetic buyer's basis-failure probability subject to a premium budget. A real finding about the optimization objective itself: an unconstrained trigger grid lets the optimizer find a degenerate near-always-pay cover that trivially drives basis-failure probability to exactly zero without being well-calibrated to real loss events — a legitimate optimum of the literally stated objective, not a bug, fixed by restricting the trigger search to the index's own historical median-to-max (a designer's judgment call the specification itself leaves open). The real case study's optimized trigger/slope/limit/premium (843.4mm / 1.0 / 10,000 / 200.1 of a 50,000 budget, firing selectively in 15 of 31 years) reproduces exactly on re-run; the specific basis-failure-probability reduction this case study originally reported (25.8% to 3.2%) does not currently reproduce, and the reason is itself a real finding reported in full in `docs/methods/parametric.md` §4 rather than silently corrected.

## 8. Limitations

**Sample size**: every physical-measure and forecasting result above rests on 31 real historical seasons — enough to be honest about, not enough to claim strong statistical power. Every write-up in this project says so explicitly rather than implying otherwise.

**Thin market**: NCDEX's rainfall contracts are new and, as far as this project can determine, not yet liquid; the market-price-of-risk estimates in §7 are consequently illustrative, not a real measured market risk premium.

**Station basis**: both contracts settle on a 2-station average; any real exposure away from those exact two points carries the basis risk measured in §7, which can be substantial even within the same metropolitan area.

**Synthetic exposures**: every hedge and parametric-cover case study uses a real location's real rainfall against the real official index, but an illustrative (not any real business's) loss exposure — stated inline wherever it appears in this document and in the dashboard.

**Reproduction discrepancies**: two real numbers from earlier write-ups (the hedge case study's exact lot count, and the parametric case study's basis-failure-probability reduction) did not reproduce exactly on re-run with the current codebase and real data; both are reported as findings in the relevant methods notes rather than quietly reconciled to match the original write-up.

**Data access restrictions**: NCDEX's settlement feed and BoM's MJO feed are both bot-gated; this project does not attempt to circumvent either, which means the market-price-of-risk and proxy-error analyses in §2 and §7 stay illustrative until that changes.

## 9. Reproducibility statement

This repository is public (research-only; see the licensing note in `docs/VERIFY.md`'s V12 entry). `make reproduce` (`mq research reproduce`) regenerates every quantitative figure in §4, §5, and §7 above from real local data, using the exact same committed engine functions the live API calls — not a separate demo code path. It needs the real IMD/ONI/DMI backfill already run locally first (`data/` is deliberately never committed to git; see `docs/STATUS.md`'s "How to resume work" for the backfill step), since "clean checkout" in this project's own stated principle means the *code* is deterministic and committed, not that zero setup is ever required for a pipeline that depends on real external data sources. `mq ledger verify` independently re-verifies the full hash chain behind §6's ledger claims. `make check` runs the full lint/type/test suite (ruff, mypy --strict, 260+ real and synthetic tests) that every commit in this repository's history passed before being merged.
